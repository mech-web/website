Announcement

Mech v0.3 — State Machines, Match, and Mika the Mech

Corey Montella ∙ April 28, 2026

Today we're announceing Mech v0.3-beta, which introduces new features for data modeling, computation, and control flow. Also, Mika the Mech is making her debut as Mech's mascot and AI assistant.

Spring is here, so that means a new version of Mech is ready! This post is mostly about the platform, but first: check out the new website design! We've only updated the blog so far, but we'll be rolling out the new design to the rest of the site in the coming weeks. I've been putting this redesign off for a number of years because it wasn't a priority next to developing the platform. But as you'll read in this update, the platform is developed enough to be ready for a wider audience.

Whereas the main focus of the just-finished v0.2 release was on the data model, the main theme of this release is control flow; we've added several new mechanisms for modeling and managing the flow of computation in Mech programs. These include:

  • Enums and tagged unions for modeling categorical data and optional values. ( §2 )

  • User-defined functions including pattern matching, recursion, and implicit broadcasting. ( §3 )

  • State machines for modeling ordered computation, protocols, and processes with phases. ( §4 )

  • Comprehensions for constructing new matrices and sets from existing ones. ( §5 )

  • Relational table joins for combining tables based on common keys. ( §6 )

  • Mika the Mech Mech's mascot and AI assistant. ( §7 )

Some of these features like enums, comprehensions, and functions are mainstays of modern programming languages. Although, in Mech each of these has a unique twist that fits with our overall philosophy and design goals. Others like state machines and relational joins are less commonly found, and they represent more research-focused experiments in ways of modeling computation that are more analyzable and debuggable.

Before we get into all that, let's first look at how v0.2 landed.

Version 0.2 Wrap-Up

Version v0.2 was completed at the end of January 2025. We didn't post a formal announcement at the time since we immediately moved on to v0.3 development, and that work was much more interesting.

We spent an inordinate amount of time on the v0.2 data model, partly because in most languages the data model is an afterthought or otherwise cargo culted. By refusing to add more features until it became painful, we were forced to stretch the data model as far as it could go. We wanted to see how expressive the language could be without Turing-completeness — leaving out core features like user-defined functions, or explicit control flow — and I think the result is quite encouraging; we were able to write programs like Kalman filters, a simple physics engine, and a live documentation system without needing a full Turing-complete language; the data model expresses a surprising amount of logic on its own.

The declarative data model for Mech has landed at the following set of features:

  • Data types and structures: number, string, atom, map, matrix, record, set, table, tuple.

  • Expression broadcasting: applying operations over data structures without explicit loops.

  • Indexing and slicing: accessing elements within data structures using logical masks.

  • Operators and standard library functions: arithmetic, logical, comparison, set, matrix etc.

You can visit any of those links to read the full1 documentation for that feature, with examples and explanations. The docs are still a work in progress, but they should give you a good sense of the capabilities of the v0.2 data model.

Of course there are strict limitations on the kinds of programs you can write with that set of features, so today we are launching Mech v0.3 with a whole new set of control flow mechanisms that make Mech more capable.

Enums, Tagged Unions, and Pattern Matching

Mech now has an enum and tagged-union system:

enums
<color>:=:red|:green|:bluex<color>:=:red

An enum is a defined kind with a fixed set of variants. Each variant is an atom which can optionally carry a payload (tag) of any kind. In the example above, <color> is an enum kind with three variants: :red, :green, and :blue. The variable x has the kind <color> and is assigned the value :red.

Because the variants are themselves valid atom values (which are program-global constants that can be used as tags or identifiers), :red is both a variant of the <color> enum and an atom value that can be used elsewhere in the program, which potentially can cause name clashes. There are tradeoffs here:

  • Allowing variants to be atoms means we don't need a separate syntax for defining and using enums, which keeps the language simpler and more uniform.

  • However, because atoms exist in a shared global space, reusing a value like :blue across different domains can introduce ambiguity or make code harder to read. To mitigate this, you can use qualified names for variants:

enums
y<color>:=:color/red

This is similar to other languages with atoms like Elixir, so Mech might have to adopt some of the same best practices around naming and organization to avoid confusion.

Tagged Unions

Tagged unions can carry payloads:

pattern-matching
<result>:=:ok<u64>|:err<u64><option>:=:some<result>|:nonex<option>:= : some ( : ok ( 42u64 ) )

In this example, two enums are defined:

  • <result> with variants :ok and :err, each carrying a <u64> payload

  • <option> with variants :some carrying a <result> payload; and :none carrying no payload.

The variable x has the kind <option> and is assigned the value : some ( : ok ( 42u64 ) ) , which demonstrates tagged union nesting.

Pattern Matching

Values wrapped inside tagged unions cannot be used directly, so we've added a match expression using the ? operator. Match allows you to destructure data by matching them to patterns, which covers the purpose of if and switch statements in other languages.

Consider the variable x<option> from the previous example. We can match on it like this:

pattern-matching
code:=x?
├ : some ( : ok ( n ) ) ⇒ n
├ : some ( : err ( e ) ) ⇒ e
├ :none ⇒ 0
└ * ⇒ 0.

The ? operator is the match operator for optional values and enum variants. If a pattern is non-exhaustive, the compiler reports the missing variants — it won't let you silently drop cases.

We can also pattern match on arrays:

pattern-array
arr:=[
1
2
3
]code:=arr?
├ [1 2 3] ⇒ "exact match"
├ [1 | tail] ⇒ "starts with 1"
├ [x y z] ⇒ "three elements"
└ * ⇒ "other".

Validation

If patterns are non-exhaustive, the compiler reports the missing variants and prevents the program from compiling, so you won't accidentally drop cases.

enums
result:=x?
└ :red ⇒ 0xFF0000.
--

Forgot to cover :blue and :green cases, so this won't compile.

Also, match arms arm return values must have the same kind, so you can't accidentally return different types from different arms.

mismatched-arms
<status>:=:running|:pending|:stoppedx:=:runningcode:=x?
├ :running ⇒ 1
├ :pending ⇒ "pending"
└ :stopped ⇒ 0.
--

This will not compile until the second arm is fixed to return a <f64> instead of a <string>.

User-Defined Functions

Functions in Mech are pure and idempotent mappings from input values to output values. They support pattern matching, recursion, tail-call optimization, and kind annotations. They also support implicit broadcasting over matrices, which means you can write a function that operates on scalars, and it will automatically apply element-wise when given matrices.

The pattern-matching style should feel familiar to anyone who has used functional programming languages like Haskell or Elm:

factorial
factorial(x<f64>) ⇒ <f64>
├0 ⇒1
└n ⇒n*factorial(n-1)
.
factorial(6<f64>)--

ans

The | arms are match guards; the first one that matches is evaluated and returned as the result of the function. You can pattern-match on multiple arguments too:

max
max(x<u64>, y<u64>) ⇒ <u64>
├ ( 0, y ) ⇒y
├ ( x, 0 ) ⇒x
└ ( x, y ) ⇒max(x-1u64, y-1u64)+1u64
.
max(4u64, 7u64)--

ans

The tree syntax (├, └) is an alternative to pipes that is more visually structured. Both styles are supported.

The value with the small yellow arrow in the above block is a new feature that allows you to print the return value of a line by putting {ans} in a comment on that line. Also, click the arrow to send the value to the console, if it's open. You can inspect the value as usual with the built-in variable ans, which is loaded as part of the REPL environment.

Implicit Broadcasting

Implicit broadcasting is also supported in user-defined functions. If you call a function with arguments that are matrices, Mech will automatically apply the function element-wise over the matrices, broadcasting as needed. This means you can write a function that operates on scalars, and it will work just as well on matrices without any extra syntax.

For example, because factorial() was defined as factorial(x) => , we can call it with a <[f64]>, and it will return a matrix of the same shape with the factorial applied to each element:

factorial
m:=[
1 3
2 4
]factorial(m)

Implicit broadcasting only applies to functions with scalar inputs and outputs. But the rule is simple:

  • If any one argument is a matrix, the function is applied element-wise over the matrix, and any scalar arguments are broadcast to match the shape of the matrix.

  • If more than one input is a matrix, all inputs must have the same shape, and the function is applied element-wise across all of them. If the shapes of all inputs don't match, the compiler will return an error.

We are still working on this design so it's subject to change. I'm unsure if this idea is good or not. We may just revert back to the idea of a broacast operator that explicitly applies a function over a matrix like Julia and Matlab, which is more verbose but also more explicit and less magical. Or, maybe the programmer has to write several overloaded versions of the function to handle different combinations of scalar and matrix arguments, which is more boilerplate but also more explicit and less error-prone.

However, since the whole language is alreay designed with implicit broadcasts in many other areas, I think we can try it here and see if it's too confusing. I just don't want to get into the issue Matlab has where the broadcasting rules are myriad and confusing. I'm hoping if we make things more consistent, it will be easier to predict when broadcasting happens.

Tail-Call Optimization

Recursive functions that call themselves in tail position are optimized through a dedicated tail-call elimination pass. This means deeply recursive functions won't blow the stack:

fib-tco
fib(n<u64>) ⇒ <u64>
└n ⇒fib-acc(n, 0u64, 1u64)
.
fib-acc(n<u64>, a<u64>, b<u64>) ⇒ <u64>
├ ( 0u64, a, * ) ⇒a
└ ( n, a, b ) ⇒fib-acc(n-1u64, b, a+b)
.

The accumulator pattern above runs in constant stack space, so we can do:

fib-tco
fib(10000u64)

The result represents an overflowed value, since the 10,000th Fibonacci number is much larger than what can fit in a u64. Mech does support u128 but not in the wasm target yet.

State Machines

A state machine in Mech has two parts: a specification that declares the states and their types, and an implementation that defines transitions.

We'll use a simple counting state machine as an example that counts down from a supplied number to zero. The specification looks like this:

counter
--

Define the state machine input, outputs, and states.

# Counter ( n<u64> ) ⇒ <u64> :=
├
:Count ( n<u64> )
└
:Done ( n<u64> )
.

This specification declares two states for the counter: :Count and :Done, each carrying a u64 value. Then, we define state machine transitions, which includes specifying the start state and its initial value, and then defining at least one transition per state. Transitions are defined using pattern matching and guards, just like in functions and match expressions. The transition rules are evaluated in order, and the first one that matches is taken as the next state.

counter
--

Define state transitions and initial state.

# Counter ( n<u64> ) → : Count ( n )
: Count ( n )
├
n>0 → : Count ( n-1 )
└
n⩵0 → : Done ( 0 )
: Done ( n ) ⇒ n
.
--

Run the state machine with a specific input.

#Counter(3u64)--

ans

The state machine continues transitioning until it either reaches a terminal state, which is indicated by a => arrow; or the transition limit is reached, which is a safety mechanism to prevent infinite loops.

Execution Tracing

State machines are a nice control flow mechanism because their formalism allows for static analysis and runtime tracing in ways that are difficult or impossible with more general control flow constructs.

One way we can check state machines is by validating that all transition targets are covered at compile time. If you reference a state that isn't declared, or you forget to handle a state, Mech returns a compile-time error.

Moreover, we have added a new --trace CLI flag which allows you to capture and print a trace of the state machine execution, showing each transition step by step, and the values on the match arm.

Example: Bubble Sort

The best way to see state machines in action is with a real algorithm. Here is bubble sort implemented as a state machine in Mech:

bubble-sort
# bubble-sort ( arr<[u64]> ) ⇒ <[u64]> :=
├
:Pass ( arr<[u64]>, acc<[u64]>, swaps<u64> )
├
:Next ( arr<[u64]>, swaps<u64> )
├
:Reverse ( arr<[u64]>, acc<[u64]>, swaps<u64> )
└
:Done ( arr<[u64]> )
.
# bubble-sort ( arr ) → : Pass ( arr, [], 0 )
--

Pass: compare adjacent elements and rebuild list in acc

: Pass ( [a b | tail], acc, swaps )
├
a>b → : Pass ( [a tail], [b acc], swaps+1 )
└
* → : Pass ( [b tail], [a acc], swaps )
: Pass ( [x], acc, swaps ) → : Next ( [x acc], swaps )
: Pass ( [], acc, swaps ) → : Next ( acc, swaps )
--

After a pass, reverse the accumulator to restore order

: Next ( arr, swaps ) → : Reverse ( arr, [], swaps )
: Reverse ( [x | tail], acc, swaps ) → : Reverse ( tail, [x acc], swaps )
: Reverse ( [], acc, 0 ) → : Done ( acc )
: Reverse ( [], acc, swaps ) → : Pass ( acc, [], 0 )
--

Return the sorted array

: Done ( arr ) ⇒ arr
.

Bubble sort works by repeatedly stepping through a list, comparing adjacent elements, and swapping them when they're out of order. We model each phase of the algorithm as a state.

To run it:

bubble-sort
a<[u64]>:=[
4
2
1
3
]sorted:=#bubble-sort(a)

The runtime validates state machine transition targets at compile time, and raises an error if you reference a state that isn't declared in the specification, or if you forget to handle a state.

Comprehensions

A comprehension is a construct for creating new data structures from existing ones using generators and optional guards. They come in two variants: matrix comprehensions and set comprehensions, which work the same but produce different kinds of output. This is useful for when you want to create something like a filtered or transformed version of an existing dataset.

Matrix Comprehensions

Here's an example of a matrix comprehension that constructs a 4x4 identity matrix:

identity-matrix
n:=4identity<[u8]:4,4>:= [ x | i ← 0..n, j ← 0..n, x:=i⩵j ]

This works by looping over each of the generated index pairs (i, j), evaluating the expression x:=i⩵j for each pair, and then collecting the results into a new matrix. The result is a 4x4 matrix where the diagonal elements are 1 (true) and the off-diagonal elements are 0 (false). The size of the output matrix is determined by the ranges of the generators, so in this case we get a 4x4 matrix because both i and j range from 0 to 4; the resulting matrix is size 1 x 16, which is then reshaped to 4 x 4 based on the specified output type.

Set Comprehensions

Set comprehensions work the same way but produce sets instead of matrices. For example, we can use a set comprehension to find the friends-of-friends in a social graph:

friends-of-friends
pairs:={(1,2), (1,3), (2,8), (3,5), (3,9)}user:=1{fof | ( u, f ) ← pairs, ( f, fof ) ← pairs, u⩵user}

This comprehension generates pairs of users and their friends, and then pairs of friends and their friends-of-friends. The fact that f appears twice in the generators creates a relational join between the two generators, which is something from the Eve language that I really liked and wanted to bring into Mech. In Eve, it would have looked like this:

search
  pairs = [user: 1, friend]
  pairs = [user: friend, fof]
bind
  [fof]

Where the search block generates pairs of users and their friends, and then pairs of friends and their friends-of-friends, and the bind block extracts the friends-of-friends. The Mech comprehension syntax is a bit more compact, but it achieves the same result.

In a future release, we plan on adding support for table and record comprehensions, which will allow you to construct new tables and records from existing ones using a similar generator and guard syntax.

Table Joins

Speaking of relational queries: v0.3 ships the full set of relational join operators, each available as both a Unicode symbol and an ASCII word alias:

  • ⋈ table/join — inner join

  • ⟕ table/left-outer-join

  • ⟖ table/right-outer-join

  • ⟗ table/full-outer-join

  • ⋉ table/left-semi-join

  • ▷ table/left-anti-join

table-joins
A:=
id<u64>
a<u64>
1 10
2 20
3 30
B:=
id<u64>
b<u64>
2 200
3 300
4 400
A⋈B

Full outer joins preserve optional kinds for columns that may be absent:

table-joins
C:=A⟗B

The a column in the second row of the output is now optional because that column is missing for the row with id=4. This means that values accessed from that column will be wrapped and cannot be accessed without unwrapping them with the ? operator:

table-joins
unwrapped:=C.a?
├ x ⇒ x
└ * ⇒ 0.

Unwrapping the optional value with ? allows us to provide a default value of 0 for any rows where the a column is missing. Also, because C.a returns a <[u64?]>, the unwrap is broadcast over the entire column, yielding a <[u64]>.

Mika the Mech

The last new feature from v0.3 I want to talk about is not a traditional language feature, but it's still a big part of the release and the Mech project generally.

Meet Mika the mech, Mechlang's first mascot:

There's enough to say about Mika that it's worth an entire post, but for now we wanted to lay out the vision and direction for this character. Mika came about early on while I was sketching out ideas for the Mech brand and identity, but I hadn't fully committed to the idea of a mascot because there are so many other things to work on.

But then I wrote a joke about a AI cat assistant, and I realized the idea of an AI language mascot could be more than just a joke if it were done properly. We already see this concept in general AI assistants, and the way people have started to personify and anthropomorphize AI tools. Claude, Copilot, and Codex all have characters which are meant to embody the personality and intelligence of the assistant, to make the attached service more approachable and relatable to users.

So it seems natural that Mech's mascot could evolve from a static character into an AI assistant that lives in the REPL and helps you write code, answers questions, or debug programs.

Character Design

Mascots are particularly useful in programming language communities because programming languages are such abstract things; what does a compiler look like anyway? How can you imagine it and describe it to someone else? What does it look like on a t-shirt? A mascot gives you a concrete image to associate with the language, which can make it more memorable and engaging. Mascots also serve as a symbol for the community and the culture around the language, which can help foster a sense of belonging and identity among users.

So a good mascot requires certain design considerations:

  • Visually appealing and memorable, so that people will want to share it and put it on stickers and t-shirts.

  • Embodies the values and personality of the brand it represents, so that it resonates with the community and reflects the spirit of the language.

  • Representable in various poses and expressions, so that it can be used in different contexts and convey different messages.

  • Possible to simplify the mascot into just a few lines and colors. So in many ways, a good mascot and a good logo share similar design goals.

Mika's design is first and foremost meant to be cute and flexible. As a robot, she can be placed in any situation or pose. Her round head and big round lens in the center of her face are distinctive and easy to recognize in various represenations. The black and yellow color scheme is high contrast and fits with Mech's wordmark branding. The name "Mika" is short and alliterates with Mech, which makes it fun to say.

These characters are mostly just cosmetic. How is Mika's integration into the language meaningful beyond mere decoration? That's where synthblocks come in:

╭⦿╯

Hello, I'm Micromika!

In source they look like this:

╭⦿╯ ⸢Hello, I'm Micromika!⸥

The idea is that Mika will eventually serve as the interface for an AI code assistant, integrated into Mech down to the source level, which will be able to understand and generate Mech code, answer questions about the language and libraries, help with debugging, and so forth. These synthblocks represent the AI responses to programmer queries, which can be embedded directly into the source code as a kind of live documentation or interactive comment that is distinguished from regular comments and code.

The AI assistant will be able to generate these blocks in response to queries, and they will be parsed and integrated into the AST, so they can be accessed and manipulated programmatically as part of the code. Any valid Mech code can be embedded inside a synthblock, which means the AI can generate code snippets that are directly executable as part of the program. For example:

╭⦿─

You had asked about how to filter a list, here's how we can do that:

filter-example
x:=[
1
2
3
4
5
]threshold:=3mask:=x>threshold

Then you can use the mask to filter the original list:

filter-example
x[mask]

Only the elements where mask is true will be included in the output.

Let me know if you need any more examples!

Then the user can reply to the AI with another query. This transforms a typical AI chat into an interactive code document, where both the user and the AI can exchange ideas and snippets that are embedded directly in the source. Everything is stored as plain text, readable without running code or using external tools, and can be version-controlled and diffed like any other source file.

What you see here is all that's been implemented so far, but the vision above is planned for the full v0.3 release.

Roadmap to v0.4

The Mech roadmap is organized into four major milestones, each representing a broad phase of development with a specific focus and set of features. The milestones are designed to build upon each other, with each one adding new capabilities and expanding the expressiveness of the language.

  • v0.1 proof of concept system - minimum viable language implementation

  • v0.2 data specification - types, structures, formulas, defining and transforming data

  • v0.3 program specification - functions, modules, state machines, Mika

  • v0.4 system specification - tools, distributed programs, capabilities

Although we've shown off a number of new and working features in this post, this is still just the beginning of the release cycle; we are still actively developing and adding features to v0.3, and we plan to be in this release cycle for at least another 6 months. After the summer, our hope is that most if not all of the current v0.3 roadmap features are implemented, and we have a full release candidate near October.
